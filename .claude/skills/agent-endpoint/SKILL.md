# Agent-Queryable API Endpoint

## Purpose

After a vCRO pipeline run completes, the intelligence sits as JSON
artifacts on disk. This skill defines the API that serves it.

The parameters are NOT fixed across runs. Each run produces its own
`endpoint_schema.json` with decision axes derived from the user's
question and the evidence found. An AD metabolomics run has different
axes than an FFPE feasibility run.

## Architecture

```
GET  /api/runs              → list available runs
GET  /api/schema?run_id=X   → dynamic parameter schema for run X
POST /api/query             → parameterized query using run-specific params
```

Agent discovery flow:

```
Agent                                  vCRO API
  |-- GET /api/runs ------------------>|  "what runs exist?"
  |<-- [{run_id, one_liner, status}] --|
  |                                    |
  |-- GET /api/schema?run_id=X ------->|  "what can I query?"
  |<-- decision_axes + fixed_params ---|
  |                                    |
  |-- POST /api/query ---------------->|  uses params from schema
  |<-- results + _endpoint block ------|  self-describing response
```

## Endpoint: GET /api/schema?run_id=X

Returns `endpoint_schema.json` for that run. This file is generated
by the deliver phase (see `vcro-deliver` Step 8.5).

The schema contains:

- `decision_axes` — run-specific parameters with values and why each matters
- `fixed_params` — parameters that work on any run (top_k, format, etc.)
- `resolution` — how each axis maps to artifact filtering
- `examples` — ready-to-use query bodies

If `run_id` is omitted, returns the schema for the latest complete run.

## Endpoint: POST /api/query

### Request body

Two kinds of parameters:

**Run-specific (from decision_axes):**
These vary per run. The API reads `endpoint_schema.json` to know
which params are valid. Examples from an AD/ALS run:
```json
{
  "disease": "AD",
  "question": "proof_points",
  "sample_type": "plasma"
}
```

**Fixed (always available):**
```json
{
  "run_id": "20260330_als_ad_metabolomics",
  "top_k": 3,
  "cohort_id": "PMC12269576",
  "include": ["recommendations", "signal"],
  "format": "summary"
}
```

| Fixed param | Type | Default | Description |
|-------------|------|---------|-------------|
| `run_id` | string | latest complete | Which run to query |
| `top_k` | integer | 5 | How many cohorts to return |
| `cohort_id` | string | null | Deep dive into one cohort by PMC/NCT ID |
| `include` | string[] | ["recommendations", "signal"] | Which sections |
| `format` | string | "full" | Response density |

Valid `include` values:
`recommendations`, `signal`, `access`, `contacts`, `provider`,
`exclusion_log`, `provenance`, `intelligence`

### Format modes

**`full`** — All requested sections with source quotes and PMC IDs.

**`summary`** — One-liner per cohort, top biomarkers, realistic AUC.

**`actionable`** — Recommendations + access routes + available_actions only.

## Query resolution logic

The API route reads `endpoint_schema.json` for the run. Resolution
rules are at the top level under `resolution`. Each key matches an
axis `param` name. Each rule has a `type` field.

Three resolution types (no others allowed):

```typescript
const schema = await readJSON(`${runDir}/endpoint_schema.json`);

for (const axis of schema.decision_axes) {
  const value = body[axis.param];
  if (!value) continue;

  const rule = schema.resolution[axis.param];

  // Type 1: field_match — filter by structural field on cohort
  if (rule.type === "field_match") {
    cohorts = cohorts.filter(c =>
      Array.isArray(c[rule.field])
        ? c[rule.field].includes(value)
        : c[rule.field] === value
    );
  }

  // Type 2: artifact_redirect — change which sections are included
  if (rule.type === "artifact_redirect") {
    const redirect = rule.values?.[value];
    if (redirect?.include) {
      include = redirect.include;
    }
  }

  // Type 3: text_search — fuzzy search in intelligence facts (fallback)
  if (rule.type === "text_search") {
    cohorts = cohorts.filter(c =>
      c.intelligence?.some(i =>
        i.fact?.toLowerCase().includes(value.toLowerCase()) ||
        i.implication?.toLowerCase().includes(value.toLowerCase())
      )
    );
  }
}
```

This replaces the old pattern where resolution rules had ad-hoc
formats (string PMC ID lists, nested dicts, match_type variants).
Three types. Dispatch on `type`. No guessing.

Old pattern that caused bugs (do NOT use):

```typescript
  if (rule[value]?.primary_artifact) {
    // The "question" axis maps values to specific artifacts
    const artifactConfig = rule[value];
    response.include = artifactConfig.include;
    if (artifactConfig.section) {
      response.section_filter = artifactConfig.section;
    }
  }
}
```

## Response headers

| Header | Value | Purpose |
|--------|-------|---------|
| `X-Package-Status` | `complete` or `partial` | Whether all pipeline phases finished |
| `Cache-Control` | `public, max-age=3600` (complete) or `no-cache` (partial) | Caching |

## What NOT to build (MVP)

- No auth (phase 2: Bearer token)
- No WebSocket for in-progress runs (agents poll status)
- No database (filesystem scan fine for <1000 runs)
- No pagination

## Gotchas

1. **Path traversal.** Sanitize run_id. Verify resolved path starts with `store/runs/`.
2. **Missing artifacts.** Not every run has every artifact. Return what exists, set `X-Package-Status: partial`.
3. **Missing endpoint_schema.json.** Older runs won't have it. Fall back to fixed params only (top_k, cohort_id, include, format).
4. **Text search is fuzzy.** Decision axis filtering via text search in intelligence facts is approximate. It works for broad categories (AD vs ALS) but not for fine-grained queries.
